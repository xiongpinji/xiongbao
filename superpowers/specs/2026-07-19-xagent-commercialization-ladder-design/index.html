X-Agent 商用成熟度三阶段推进设计

  • 日期：2026-07-19
  • 主题：将 xagent 从当前准商用 / 试点可交付状态，分阶段推进到正式商用与企业级长期运营
  • 当前主方案：方案 A / 三阶段串行推进
  • 适用范围：xagent 当前代码仓、交付流程、发布治理、长期运营能力

1. 背景与问题定义

当前 xagent 的唯一事实源与发布检查材料表明：

  • 项目已经不是原型，具备主链可运行、功能版图完整、内部试点 / 受控交付基础；
  • Spine Phase 1 已完成并合并，说明目标任务板、session、release summary、前端 Goal Board 等主交付骨架已落地；
  • 但项目整体仍不应直接宣称为“正式商用 GA”，因为距离发布级、长期运营级仍有明确缺口。

当前缺口不再主要体现在“有没有功能”，而体现在：

  1. 内部试点级可稳定日常使用 是否真正闭环；
  2. 正式商用 GA 所需的版本冻结、目标环境演练、签字与治理闭环是否完成；
  3. 企业级长期运营 所需的 HA、K8s、SLO、告警、审计保留、扩缩容边界是否具备。

因此，当前需要的不是继续把“商用”当作一个模糊大目标，而是把它拆成三个可验收、可执行、可逐段推进的里程碑。

2. 设计目标

本次设计目标是：

为 xagent 定义一条从“当前准商用状态”到“商用程度百分百”的清晰三阶段路径，确保每一阶段都有明确范围、验收门和不做事项，避免项目无限膨胀。

2.1 总目标

三阶段路径固定为：

  1. Phase 1：内部试点可稳定使用
  2. Phase 2：正式商用 GA
  3. Phase 3：企业级长期运营

2.2 设计原则

  1. 先验收边界，再开工：避免把“商用”理解成无限 backlog；
  2. 先保主链，再保完美：优先保证常用链路、稳定性、恢复与治理；
  3. 阶段只做阶段该做的事：不提前把后续阶段的高阶能力塞入前置门；
  4. 以现有事实源为准：所有判断必须对齐 COMMERCIAL_STATUS_SOURCE_OF_TRUTH.md 与发布检查表；
  5. 每阶段必须可签字：不仅要实现，还要能被负责人判断是否通过。

3. 方案选择

3.1 候选方案

方案 A：按商用成熟度分三阶段串行推进（推荐）

  • Phase 1：内部试点可稳定使用
  • Phase 2：正式商用 GA
  • Phase 3：企业级长期运营

方案 B：按风险域并行推进

  • 功能链路线
  • 稳定性线
  • 数据 / 权限 / 审计线

方案 C：按交付对象推进

  • 内部试点包
  • 付费私有部署包
  • 企业级运营包

3.2 为什么推荐方案 A

方案 A 最符合当前项目现状与用户要求：

  • 用户已经明确要求按 1 -> 2 -> 3 顺序推进；
  • 项目当前最缺的是阶段门与验收边界，而不是更多并行拆分；
  • 串行推进更适合把“试点可用”“正式可发布”“长期可运营”三种完全不同的完成标准拆开；
  • 它能最大程度避免 Phase 1 被 HA/K8s 等后置能力拖住，也避免 Phase 2 被长期运营治理无限扩张。

因此，本设计采用：

方案 A：三阶段串行推进。

4. Phase 1：内部试点可稳定使用

4.1 目标

Phase 1 的目标不是“全部商用能力就绪”，而是：

内部团队能够连续日常使用，核心链路可跑，出现问题可定位、可恢复、可追责。

4.2 功能边界

必须稳定可用

  • 登录 / 鉴权
  • 核心工作台进入
  • task / run / workflow 主链路
  • 关键结果查看与回放
  • 关键配置页 / 索引页
  • 最常用 1-2 条业务路径端到端打通

暂不追求终局

  • 所有高级功能都打磨完
  • 所有视觉与交互细节完全统一
  • 所有实验能力都纳入试点范围

4.3 稳定性边界

必须具备

  • 常用操作不会频繁报错
  • 任务失败时有明确失败态
  • 失败后可恢复、可重试、可解释
  • 后端 / 前端关键错误可被日志或 evidence 捕获
  • 已知故障有 runbook 或处理办法

暂不强求

  • 企业级 HA
  • 自动扩容
  • 极限压测结论
  • 多集群容灾

4.4 数据 / 权限 / 审计边界

必须成立

  • 租户隔离不会明显穿透
  • 权限模型能阻止低权限访问高权限能力
  • 关键操作有可追溯记录
  • 关键运行态与交付态有 evidence / run / task 可回查
  • 默认危险配置不能直接带入试点环境

4.5 Phase 1 验收门

Gate A：功能门

  • 关键内部试点路径全通
  • 至少 1 组标准日常使用场景可重复演示
  • 无必须人工绕路的 P0 断点

Gate B：稳定性门

  • 常用链路在连续验证中稳定
  • 失败态与恢复路径可验证
  • 关键报错不是静默失败

Gate C：权限与可追溯门

  • 核心权限边界验证通过
  • run / task / workflow / evidence 能回查
  • 关键高风险动作有记录

Gate D：试点交付门

  • 内部试点部署说明可执行
  • 已知问题清单可读
  • 运维/排障最小手册存在
  • 有明确“不建议对外宣称什么”的口径

4.6 Phase 1 不做

  • 不把它定义成正式 GA
  • 不把 HA / K8s / 多集群作为 Phase 1 前置
  • 不要求所有功能都达到最终视觉 / 交互形态
  • 不要求完整企业级运营体系一步到位

5. Phase 2：正式商用 GA

5.1 目标

Phase 2 目标不是新增大量功能，而是：

让已经可内部试点的系统，进入可正式对外承诺、可标准化交付、可被发布负责人签发的状态。

5.2 核心变化

Phase 1 解决“可用”， Phase 2 解决“可发布”。

必须成立

  • 版本冻结清楚
  • 目标环境证据真实
  • 发布 / 回滚流程可执行
  • 运维与交付口径一致
  • 可以正式签字

5.3 功能层要求

必须成立

  • 首发范围冻结
  • 对外交付的功能边界明确
  • 不再依赖内部调试口径解释系统
  • 关键用户路径在目标交付环境中重新验证

5.4 发布与恢复要求

必须具备

  • 版本候选冻结
  • 候选对应远端 CI 全绿
  • 目标环境 / 等价环境演练完成
  • 发布 Runbook 可执行
  • 回滚 Runbook 可执行
  • 常见故障处置路径明确
  • 发布后验证清单明确

必须避免

  • 把本地证据误写成正式发布证据
  • 把历史完成误写成当前环境完成
  • 把“差不多能发”当成“正式签字可发”

5.5 数据 / 权限 / 审计要求

必须成立

  • 交付环境下权限边界成立
  • 默认危险配置彻底清零
  • 关键操作审计与 evidence 可支持复盘
  • secret / config 注入方式可交付、可复现
  • 不依赖本地临时口径维持安全性

5.6 文档与签字要求

必须完成

  • 唯一事实源
  • 发布检查表
  • 交付材料索引
  • 部署手册
  • 运维手册
  • 已知问题与试点边界说明
  • 最终 PR / release 审查包
  • reviewer / owner 可签字入口

5.7 Phase 2 验收门

Gate A：候选冻结门

  • 交付范围固定
  • 远端 CI 对应当前候选
  • 无范围漂移

Gate B：发布演练门

  • 目标环境或等价环境演练通过
  • 发布 / 回滚 / Smoke / 恢复流程可执行
  • 有证据归档

Gate C：交付治理门

  • 文档口径一致
  • 权限 / secret / defaults 达到正式交付要求
  • reviewer 能基于材料独立判断

Gate D：签发门

  • PR / release 包完整
  • owner / 发布负责人可签字
  • 可以正式对外承诺该版本

5.8 Phase 2 不做

  • 不把 HA / K8s / 多集群作为 GA 前置
  • 不把企业长期运营治理全部塞进 GA 前
  • 不要求所有未来增强项在 GA 前完成

6. Phase 3：企业级长期运营

6.1 目标

Phase 3 的目标已经不是“能发布”，而是：

系统能够长期、持续、规模化地运营，而不是靠单次发布成功维持。

6.2 核心关注点

这一阶段重点从： - 功能是否能交付 - 发布是否能签字

转为： - 系统是否能长期稳定运行 - 能否承载更多租户 / 更多任务 / 更复杂环境 - 出问题时能否快速发现、定位、控制、恢复 - 是否有运营成本和治理边界

6.3 基础设施与架构要求

必须具备

  • HA / 多实例验证
  • K8s 或等价长期运行编排能力
  • 多副本下状态一致性验证
  • 幂等 / 重试 / 补偿链路在规模化下仍成立
  • 关键依赖的容量、超时、退避、熔断策略明确

6.4 可观测与运维要求

必须具备

  • 指标 / 日志 / Trace 可用
  • SLI / SLO 设计
  • 告警策略
  • 常见故障快速定位路径
  • 异常高负载 / 外部依赖波动时的监控与降级策略

6.5 数据 / 审计 / 合规要求

必须具备

  • 审计保留策略
  • 数据保留 / 清理 / 生命周期规则
  • 权限模型在长期运营中的演进策略
  • 多租户边界在规模上成立
  • 合规性资料能支持更正式场景

6.6 成本与容量要求

必须回答

  • 成本是否可控
  • 扩容边界在哪里
  • 哪些依赖是瓶颈
  • 哪些链路需要配额 / 限流 / 优先级策略

6.7 Phase 3 验收门

Gate A：长期运行门

  • 多实例 / 长时间运行验证通过
  • 关键状态链不因长期运行而漂移

Gate B：可观测门

  • 指标 / 日志 / Trace / 告警闭环成立
  • 故障可以被发现，而不是靠用户报错才知道

Gate C：治理门

  • 审计、权限、保留策略可长期执行
  • 不依赖临时人工习惯维持秩序

Gate D：扩展门

  • 成本 / 容量 / 限流 / 扩缩容边界明确
  • 可以支持更大范围租户或业务增长

6.8 Phase 3 不做

  • 不把所有组织级协作能力一次性做完
  • 不把所有未来商业模式都提前实现
  • 不把插件市场、全生态平台化当成此阶段前置

7. 三阶段之间的推进关系

7.1 顺序关系

  • 未通过 Phase 1，不进入 Phase 2；
  • 未通过 Phase 2，不进入 Phase 3；
  • 三阶段是成熟度递增关系，不是平行可跳跃关系。

7.2 输出物关系

  • Phase 1 输出：试点可日常使用的系统与最小交付材料；
  • Phase 2 输出：正式商用可签发版本；
  • Phase 3 输出：企业级长期运营能力。

7.3 管理关系

  • 每个阶段都必须有独立任务板 / 验收门 / 证据包；
  • 每个阶段结束时必须能明确回答“当前允许对外怎么说、不允许怎么说”。

8. 推荐推进方式

建议接下来先做：

  1. 从当前项目状态反推 Phase 1 尚未完成的缺口清单；
  2. 将这些缺口按：
  3. 功能链路
  4. 稳定性 / 恢复
  5. 数据 / 权限 / 审计
  6. 试点交付材料 四组拆开；
  7. 为 Phase 1 产出一份专门实现计划；
  8. 只有在 Phase 1 验收门通过后，再开始设计 / 执行 Phase 2 的正式 GA 收口计划。

9. 当前结论

xagent 不应该再以“是否已经全部完成”来管理，而应以“当前处于哪一个商用成熟度阶段、这一阶段的门是否通过”来管理。

采用三阶段串行推进（内部试点可稳定使用 → 正式商用 GA → 企业级长期运营），可以把当前准商用项目拆解成可执行、可验收、可签字的剩余工作路径。
