G3-C4 容量 / 扩展边界真实验证计划

适用阶段：G3 企业级长期运营

用途：把 G3-C4 从“容量与扩展边界已定义”推进到“可执行验证”，明确当前哪些容量入口、负载验证与瓶颈对象可以被真实验证，以及哪些仍只是后续目标。

1. 目标

本计划的目标是：

为 xagent 的容量 / 扩展边界包提供第一份真实验证计划，使 G3-C4 不再只停留在定义层，而进入可验证状态。

2. 验证范围

本次验证只覆盖：

  1. 当前是否已有真实可执行的基础负载验证入口；
  2. 当前性能与容量检查项是否已被明确写入正式材料；
  3. 当前瓶颈对象是否已被正式列出；
  4. 试点 / 灰度 / 企业级规模边界是否已可解释；
  5. 团队是否已经知道哪些结论是“已验证”，哪些只是“后续目标”。

本次验证不要求一次性完成： - 全量压测平台建设； - 完整生产级性能基线签字； - 所有扩缩容策略自动化； - 多地域 / 大规模容量实测。

3. 验证环境

当前优先采用：

  • 仓库文档与现有命令入口的等价验证环境；
  • 用于确认负载测试入口、性能与容量检查条目、瓶颈对象和扩展边界是否已形成真实材料基础。

环境前提： - 能读取 COMMERCIAL_RELEASE_CHECKLIST_V1.md 中性能与容量项； - 能读取 OPERATIONS_MANUAL_V1.md 中与 worker / warmup / 依赖相关的运维边界； - 能确认是否存在至少一个真实可执行的负载验证入口（如 locust）。

4. 验证项

4.1 负载验证入口

检查： - 是否已存在真实可执行的负载入口，例如：

cd apps/api
locust -f tests/load/locustfile.py --host http://localhost:8000 --headless -u 50 -r 5 -t 60s

期望： - 至少存在一个被正式文档引用的负载测试入口； - 该入口不是口头设想，而是已经写入计划 / 检查表 / 材料。

4.2 性能与容量检查项

验证 COMMERCIAL_RELEASE_CHECKLIST_V1.md 中是否已明确： - 至少一轮负载测试； - 基础容量结论（如 10/50/100 并发建议）； - API / worker / LLM / Redis / Qdrant 的主要瓶颈点； - 试点用户规模与限制条件。

期望： - 容量问题不再是完全空白； - 至少有正式的检查项存在。

4.3 运维边界与瓶颈对象

验证 OPERATIONS_MANUAL_V1.md 中是否已经明确： - worker pending - LLM timeout / warmup - provider 路径问题 - 依赖不可用时的观察方式

期望： - 团队已经有最小瓶颈认知，不会在长期运营阶段完全盲开规模。

4.4 规模边界表达

确认当前包中对： - 试点规模 - 灰度规模 - 企业级规模 的分界是否已被正式写出。

期望： - 不再把“可试点”误说成“可无限扩展”； - 不再把“以后再压测”误写成“已知容量边界”。

5. 通过标准

G3-C4 的真实验证通过，至少需要满足：

  1. 负载验证入口已真实存在并被正式引用；
  2. 容量检查项已被正式列出；
  3. 关键瓶颈对象已被明确；
  4. 试点 / 灰度 / 企业级规模边界已有可解释表达；
  5. 可以明确区分“当前已有基础”与“后续仍需真实压测的部分”。

这意味着： - G3-C4 的“通过”不是所有容量结论都已经被完整实测； - 而是长期运营阶段的容量验证已经进入真实可执行状态。

6. 证据要求

本计划要求输出的最小证据包括：

  • 当前负载验证入口说明
  • 检查表中的性能 / 容量条目确认结果
  • 当前主要瓶颈对象清单
  • 试点 / 灰度 / 企业级规模边界确认结果
  • 最终判定：
  • 通过 / 不通过
  • 哪些部分已验证
  • 哪些仍是后续目标

建议归档到： - docs/coordination/reports/commercialization-g3-c4-capacity-verification.md

7. 当前结论

当前 G3-C4 已完成方向定义； 这份计划的作用是让它进入下一状态：

可执行验证

只有完成这一步，G3-C4 才能从“定义完成”走向“验证完成”。
