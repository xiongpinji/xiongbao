Phase 1 商用缺口清单与冻结范围

用途：把 xagent 当前从“已具备内部试点基础”推进到“Phase 1 内部试点可稳定使用”所需的剩余工作冻结成可执行清单。本文只覆盖 Phase 1，不讨论 Phase 2 / Phase 3 的长期运营增强。

结论先行：当前 Spine Phase 1 主链、Goal Board、release summary、session decision、权限边界和最小 CI 基线已经形成，Phase 1 的剩余工作重点已经从“补主功能”转为“把内部试点所需的稳定性、可追溯性、交付材料和验收口径收紧为可签字状态”。

1. Phase 1 冻结定义

Phase 1 的完成标准不是“功能越多越好”，而是：

  • 内部团队可以连续日常使用关键主链；
  • 常见失败态可以看到、定位、恢复；
  • 关键权限 / 租户 / 审计边界可以回查；
  • 试点交付材料可以直接给管理员 / 运维 / 接手者使用；
  • 不再依赖口头说明去解释哪些能力算交付范围、哪些不算。

因此，Phase 1 的剩余任务应冻结为四组：

  1. 功能链路缺口；
  2. 稳定性 / 恢复缺口；
  3. 数据 / 权限 / 审计缺口；
  4. 试点交付缺口。

2. 当前状态判断

当前仓库已确认的事实包括：

  • Spine Phase 1 的主链能力已经落地：goal board API、run/task/workflow 状态挂接、session resume 决策、release packaging summary、前端 Goal Board 主控制面、Release / Recovery 侧栏。
  • 当前已具备内部试点 / 受控私有部署的底座，但还没有把所有试点验收口径冻结成正式 Phase 1 收口门。
  • 现有文档已经覆盖了真实状态、发布检查表、运行手册、环境基线、已知问题与试点边界，但这些材料仍需要以 Phase 1 缺口清单为中心重新对齐。

换句话说：Phase 1 的主要缺口不是“再造新模块”，而是“把现有模块与文档、测试、验收门重新冻结成一套能交付内部试点的包”。

3. 功能链路缺口

目标：内部试点的高频主链可以稳定完成，不需要人为绕路。

剩余任务

  • 固定一条内部试点的标准日常使用路径：登录 → 工作台 → 任务/工作流/运行视图 → 结果查看/回放。
  • 确认 Phase 1 主入口中，Goal Board、Run Console、工作流入口、设置页和任务提交入口的导航一致性。
  • 确认 release / recovery 侧栏只承载发布相关状态，不把全局 next action 误导到发布区块。
  • 将关键路径对应的页面 / API / 测试清单收敛到一套最小试点脚本，避免依赖临时探索式操作。

完成定义

  • 内部人员可按同一脚本反复完成一次试点日常操作。
  • 不需要看源码或问开发者即可理解入口位置。
  • 主链上的错误能在 UI 中看到明确反馈，而不是跳转失败或静默空白。

4. 稳定性 / 恢复缺口

目标：试点环境下出现故障时，能看见、能恢复、能解释。

剩余任务

  • 对任务失败、工作流失败、运行详情加载失败、迁移失败等场景保留一致的失败态展示。
  • 将“失败 → 定位 → 恢复 / 重试”形成可复用的最小演练脚本。
  • 确认 worker / runtime / spine 的失败状态回写路径在测试中稳定，不依赖偶发的人工修补。
  • 保证前端测试支撑、后端迁移辅助、CI lint / test 路径和目标代码一致，不让试点验证依赖未同步的测试桩。

完成定义

  • 常见失败不是黑盒崩溃，而是有明确状态和建议动作。
  • 失败态能在 Run Console / Goal Board / 任务详情里回查。
  • 至少完成一次从失败到恢复的人工演练，并留下证据。

5. 数据 / 权限 / 审计缺口

目标：内部试点可以放心在多人、多租户、可追溯的前提下使用。

剩余任务

  • 把 spine 资源的权限边界、viewer / member / admin 能力差异与现有运行时权限策略在文档中统一说明。
  • 明确 run / task / workflow / evidence 的回查关系，避免内部试点只看 UI 不知道底层证据在哪里。
  • 对现有“可追责”要求做一次最小审计链确认：谁发起、谁执行、结果落到哪里、失败如何追查。
  • 把试点环境中哪些默认值必须禁用、哪些 secret 必须显式注入写成统一清单，而不是散落在 compose、Helm 和 README 中。

完成定义

  • 租户隔离、权限边界、审计入口与 run/task/evidence 关系能被非开发者读懂。
  • 试点环境不会因为默认值 / 权限绕过 / secret 漏配而看起来“能跑但不可信”。
  • 出现问题时，能从文档和系统记录追到具体对象。

6. 试点交付缺口

目标：把 Phase 1 从“能用”变成“能交付给内部试点 / 受控私有部署的最小包”。

剩余任务

  • 把管理员部署手册、运维手册、升级 / 回滚说明、已知问题与试点边界、联系与故障升级路径这五类材料作为 Phase 1 交付包固定下来。
  • 将目标环境 / full-mode 演练与证据归档要求写入试点交付定义，而不是留给后续 GA 才补。
  • 把内部试点允许做什么、不允许做什么、出问题找谁，写成可直接复制给试点负责人的说明。
  • 明确哪些试点材料已经 READY，哪些还只是“可参考”，避免内部误把 ready 材料当作正式签字。

完成定义

  • 试点负责人拿到材料后，可以独立完成部署、日常值守和一次恢复演练。
  • 所有试点边界有明确文字说明。
  • 不需要开发者陪跑才能启动试点。

7. Phase 1 冻结边界

Phase 1 冻结后，以下内容不应再被当成 Phase 1 缺口：

  • Phase 2 的正式商用 GA 冻结、目标环境演练、PR 签发；
  • Phase 3 的 HA / K8s / SLO / 容量 / 审计保留；
  • 未被纳入试点范围的实验性前端或平台化能力；
  • 任何需要另起专项才能证明的企业级治理能力。

换句话说，Phase 1 只关心：

内部试点能不能稳定、可追责、可交付地用起来。

8. Phase 1 执行次序建议

建议 Phase 1 的后续实现顺序是：

  1. 冻结这份缺口清单；
  2. 先补“功能链路”与“稳定性 / 恢复”相关的可见缺口；
  3. 再补“数据 / 权限 / 审计”的收口；
  4. 最后把试点交付材料整理成可交接包；
  5. 完成一次内部试点演练并记录结果。

9. 当前结论

Phase 1 的剩余工作已经可以明确为一套小而完整的收口路径：

  • 功能链路要稳定；
  • 失败态要可恢复；
  • 数据 / 权限 / 审计要可追责；
  • 试点交付材料要可直接使用。

这份清单就是后续 Phase 1 执行任务的起点。
