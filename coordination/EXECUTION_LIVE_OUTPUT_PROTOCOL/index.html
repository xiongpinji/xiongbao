EXECUTION LIVE OUTPUT PROTOCOL

1. 目标

本协议用于补齐共享任务板体系中的“准即时通信”能力。

目标不是让 Claude Code / Codex 直接共享会话，而是让执行会话把关键状态、问题、恢复条件和下一步动作即时落盘，使总调度不依赖用户转述聊天内容，也能及时掌握真实状态并做调度判断。

2. 与现有文档的关系

  • README.md：协作入口与阶段目标
  • TASK_BOARD.md：生命周期状态、任务分配、依赖、阻塞
  • TASK_PACKAGE_PROTOCOL.md：领取/实施/交付/验收规则
  • reports/delivery-report.md：正式交付证据与剩余风险
  • EXECUTION_LIVE_OUTPUT_PROTOCOL.md：执行会话的准即时状态暴露协议

本协议不替代任务板和交付记录，而是定义：

  • 哪些状态必须即时落盘
  • 什么时候更新
  • 更新到哪里
  • 总调度如何消费这些信息

3. 总调度必须能看到什么

对任何 CLAIMED / IN_PROGRESS / BLOCKED / REVIEW 任务，总调度至少要能从仓库里读到：

  1. 当前在做什么
  2. 做到哪一步
  3. 正在跑什么验证
  4. 卡在哪里
  5. 恢复需要什么条件
  6. 下一步建议是什么
  7. 这些信息对应的证据或报告锚点在哪

如果上述内容只存在于聊天窗口，而不在仓库文档中，总调度一律视为：

状态暴露不足

4. 标准 live 回执结构

所有活跃任务卡在 TASK_BOARD.md 中，除首行任务卡外，还必须有一条紧跟的 live 回执行。

推荐格式：

live: <ISO时间> | substate: WORKING/VERIFYING/WAITING_DEP/WAITING_REVIEW/HANDOFF_NEEDED | action: <当前动作> | risk: <一句话风险/阻塞> | next: <下一步建议> | due: <下次心跳截止> | detail: <报告锚点>

字段含义

  • ISO时间：最后一次真实状态更新时间
  • substate：活跃子状态
  • action：当前正在执行的动作
  • risk：当前主要风险或阻塞
  • next：下一步建议或等待对象
  • due：下次必须更新状态的截止时间
  • detail：详细报告或交付节锚点

5. 执行会话必须即时落盘的事件矩阵

以下事件发生时，必须在同回合或 5 分钟内更新任务板 live 回执；必要时同步更新任务专属报告或 delivery-report.md。

A. 领取任务

  • READY -> CLAIMED
  • 必须落盘：Owner、开始时间、工作树、第一步动作、首个 due

B. 开始执行

  • CLAIMED -> IN_PROGRESS
  • 必须落盘：当前动作、依赖、当前关注点

C. 开始长时验证

  • 例如 build / test / CI / rehearsal
  • 必须先写“开始验证”回执，不允许等跑完才统一补

D. 验证出结果

  • 成功 / 失败 / 仅部分通过
  • 必须落盘：命令、结果、影响范围、下一步建议

E. 发现阻塞

  • 必须同步：阻塞原因、需要谁决策、恢复条件、下次检查点
  • 若阻塞会影响后续任务，总调度应据此拆 U* 或新 R* 包

F. 发现范围漂移

  • 不允许隐式扩包
  • 必须先落盘：跨包影响、是否建议拆新卡、当前包是否继续推进

G. 进入 REVIEW

  • 同一回合必须已有 delivery-report.md 对应任务节
  • 至少补齐：验证命令、验证结果、Reviewer 关注点、剩余风险、下一步建议

H. 进入 DONE

  • 必须说明：未闭环风险是否已转新卡
  • 不能把仍需外部动作的任务直接 DONE

6. 心跳与超时规则

6.1 活跃执行心跳

  • 任务处于 IN_PROGRESS
  • 且子状态为 WORKING / VERIFYING
  • 最长 15 分钟必须刷新一次 live 回执

如果即将启动预计超过 15 分钟的测试 / 构建 / CI / rehearsal： - 先写“开始验证”回执 - 再在“结束时”或“20 分钟到达时”二选一先到即更新

6.2 CLAIMED 超时

  • READY -> CLAIMED 后
  • 10 分钟内必须转 IN_PROGRESS 或 BLOCKED
  • 否则总调度视为“占坑未暴露进展”

6.3 BLOCKED 心跳

  • BLOCKED 项最长 60 分钟刷新一次
  • 若恢复条件、决策人、依赖状态变化，必须立即更新，不等到下个周期

6.4 REVIEW 等待心跳

  • REVIEW 项若 120 分钟内没有验收结果
  • Owner 或总调度至少更新一次：
  • 现在在等什么
  • 若退回先看什么
  • 下一步动作建议

否则视为 reviewer 等待态不可见。

7. 状态暴露不足的判定标准

满足任一即可判定：

  1. 没有 live 第二行
  2. 最近回执 超过心跳上限
  3. due 已经过期
  4. detail 锚点缺失或失效
  5. BLOCKED 无恢复条件
  6. REVIEW 无 delivery-report.md 对应任务节
  7. 任务专属报告已暴露新风险/恢复条件，但任务板未同步
  8. 关键状态只存在于聊天，不存在于任务板/交付记录/专属报告

出现以上情况时，总调度应： - 先黄灯提醒补盘 - 超过 1 个完整心跳周期仍不补齐，则升级为 failure signal

8. Failure signals（总调度直接判异常）

以下情况总调度应直接视为 failure signal：

  1. 活跃任务超过心跳期限仍无回执
  2. REVIEW 无证据节，或证据节缺命令/结果/剩余风险/reviewer 关注点
  3. BLOCKED 缺阻塞原因 / 恢复条件 / 决策人 / 检查点
  4. delivery-report.md 暴露了新 blocker、新风险，但任务板没同步新状态或新任务
  5. 同一 live 心跳连续两个周期完全重复，且没有升级动作
  6. gate 依赖已满足，但任务仍无故不推进

9. 任务专属报告何时必须创建

出现以下任一情况时，必须单独创建任务专属报告，并在 live 回执 detail 中引锚：

  1. 问题描述超过一句话
  2. 验证链条较长
  3. 阻塞恢复步骤较多
  4. 需要记录结构化 triage/差异归因
  5. 需要供 reviewer 或总调度重复引用

例如： - R10_FULL_FLOW_E2E_TRIAGE.md - R16_FULL_MODE_REHEARSAL_PREP.md - R17_PR_EVIDENCE_MATRIX_SOURCE.md

10. 总调度消费顺序

总调度固定按以下顺序读取：

  1. TASK_BOARD.md
  2. Board Meta
  3. Blocked
  4. Ready for Review
  5. In Progress
  6. Ready to Claim
  7. 每张活跃卡的 live 回执
  8. delivery-report.md
  9. 任务专属报告锚点
  10. 事实源与发布门禁文档

总调度动作

  • 若 next、risk、恢复条件 暴露新缺口，立即补 READY 或 U* 包
  • 不等用户手工转述聊天记录
  • 不把未落盘的口头说明当成正式状态

11. delivery-report 模板扩展建议

每个交付节除现有字段外，增加：

  • 关联 live 回执 / 专属报告
  • 下一步动作建议

这样总调度能把： - 实时状态 - 最终交付 - 后续补单

串成闭环。

12. 红线

  • 关键状态只在聊天里说，不落盘
  • 长时验证开始后不写“开始验证”回执
  • 阻塞只写“卡住了”，不写恢复条件
  • REVIEW 没证据节
  • live 心跳长期不更新
  • delivery-report 暴露新风险，但任务板不建新卡/不改状态

出现以上任一项：总调度应判状态暴露不足，并要求立即补齐。
