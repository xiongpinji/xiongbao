前端未提交改动收口清单（2026-07-03）

适用范围：apps/web 当前未提交改动。 目标：明确页面验收 checklist、两次提交方案，以及需要补“预览 / 演示态”标识的页面。

1. 页面验收 checklist

执行顺序：先过导航与登录，再过核心路径，最后过演示 / 辅助页面。

A. 登录与进入路径

  • [ ] 打开 /login，检查登录页布局、Logo、文案、按钮状态是否正常。
  • [ ] 使用 admin / admin 登录，确认跳转到 /chat。
  • [ ] 点击“匿名进入工作区”，确认可进入 /chat。
  • [ ] 匿名进入后刷新页面，确认匿名态仍然有效。
  • [ ] 执行清 Token / 退出后，确认重新回到登录态。

B. 路由兼容与 Professional Mode

  • [ ] 访问 /workflows，确认自动跳转到 /professional?mode=workflow。
  • [ ] 访问 /creative，确认自动跳转到 /professional?mode=drama。
  • [ ] 访问 /canvas，确认自动跳转到 /professional?mode=drama。
  • [ ] 访问 /home，确认等价进入 /chat。
  • [ ] 在 /professional 内切换 mode=workflow / mode=drama，确认页面、顶部导航、右侧上下文不异常。
  • [ ] 从 Professional Mode 跳到 /editor，确认高级剪辑页入口正常。

C. 核心执行链路

1）Chat

  • [ ] 输入任务并提交，确认 loading、SSE 输出、最终结果展示正常。
  • [ ] 模拟 SSE 失败，确认是否回退到普通 runAgent。
  • [ ] 成功后点击“查看运行详情”，确认进入 /runs/:runId。
  • [ ] 失败时确认错误信息可见、不会卡死在 loading。

2）Workflow

  • [ ] 手动新增步骤，确认步骤列表与画布节点同步。
  • [ ] 通过对话助手新增步骤，确认也能同步到画布。
  • [ ] 删除步骤，确认节点与连线同步删除。
  • [ ] 创建并执行，确认跳转 /runs/:runId。

3）Creative / Drama

  • [ ] 输入 brief 创建画布，确认节点生成正常。
  • [ ] 运行 produce，确认结果、运行跳转、时间线相关状态正常。
  • [ ] 检查失败提示是否可见、不会吞错。

4）Run Detail

  • [ ] 正常打开有效 runId，确认 Run Console 渲染完整。
  • [ ] 打开无效 runId，确认 fallback 页显示正常。
  • [ ] 缺少 runId，确认 fallback 文案合理。
  • [ ] 点击“重试 / 返回对话 / 打开工作流”，确认跳转行为正常。

D. 导航壳层与布局

  • [ ] 左侧 Collapsed Rail 图标、激活态、hover 态正常。
  • [ ] Workspace Sidebar 在展开 / 折叠之间切换正常。
  • [ ] TopBar 在中小屏 / 大屏下布局不挤压。
  • [ ] 右侧 Context Panel 在 xl 以上显示正常，xl 以下隐藏后主流程仍可用。
  • [ ] 黑金主题下输入框、按钮、边框、弱提示文本对比度可接受。

E. 演示 / 辅助页面

  • [ ] Agents 页：接口成功时显示真实角色；失败时显示 fallback 角色，并有明确提示。
  • [ ] Memory 页：对话助手跳转到 settings?section=index&tab=knowledge 是否符合预期。
  • [ ] Open Source 页：对话助手跳转到 settings?section=index&tab=open-source 是否符合预期。
  • [ ] Settings 页：左侧 section 切换正常；“配置助手”不会误导为真实执行入口。

F. 已跑过的基线验证

  • [x] npm --prefix "...\apps\web" run typecheck
  • [x] npm --prefix "...\apps\web" run build
  • [ ] 如需补充体验验证，可再做一次实际页面点击验收。

2. 两次提交方案

提交 1：壳层 / 导航 / 主题重构

目标： 先把统一工作区的框架收口，不混入太多页面内部交互逻辑。

建议包含文件：

  • src/App.tsx
  • src/api/client.ts
  • src/shell/shellRoutes.ts
  • src/components/layout/AppShell.tsx
  • src/components/layout/CollapsedRail.tsx
  • src/components/layout/TopBar.tsx
  • src/components/layout/WorkspaceSidebar.tsx
  • src/components/layout/ShellContextPanel.tsx
  • src/components/effects/AmbientAurora.tsx
  • src/index.css
  • src/pages/LoginPage.tsx
  • src/pages/ProfessionalModePage.tsx
  • public/assets/xiongbao-logo.png
  • public/assets/xiongbao-mascot.png

建议 commit 主题：

feat(web): unify shell, theme, and professional mode navigation

提交 2：页面内对话式交互增强

目标： 在新壳层基础上，单独收口各页面的“对话驱动入口”。

建议包含文件：

  • src/components/chat/ConversationalCommand.tsx
  • src/components/runs/RunConsole.tsx
  • src/components/settings/SettingsLayout.tsx
  • src/components/settings/GeneralSettings.tsx
  • src/pages/ChatPage.tsx
  • src/pages/AgentsPage.tsx
  • src/pages/WorkflowsPage.tsx
  • src/pages/CreativeStudioPage.tsx
  • src/pages/RunPage.tsx
  • src/pages/MemoryPage.tsx
  • src/pages/OpenSourcePage.tsx
  • src/pages/EditorPage.tsx

建议 commit 主题：

feat(web): add conversational entry points across workspace pages

拆分原则

  • 提交 1 解决“壳子与导航是什么”。
  • 提交 2 解决“页面内部怎么交互”。
  • 如果提交 2 中有较多 demo / fallback 逻辑，也可进一步拆成“真实执行入口”和“辅助页对话入口”两次提交。

3. 需要补“预览 / 演示态”标识的页面

原则：凡是 UI 看起来像“真实智能助手”，但当前主要做本地回显、导航辅助、fallback 展示的，都应该明确标注。

优先补标识的页面

A. AgentsPage

原因： - 接口失败时会展示 fallbackRoles。 - 页面看起来像可以真正调度多个智能体。

建议文案： - “当前为角色预览模式” - “当后端角色接口不可用时，展示本地演示角色”

B. MemoryPage

原因： - 当前对话助手主要是导航与建议，不是真正返回检索结果。

建议文案： - “当前助手用于引导检索流程，不直接展示真实知识库结果” - 或 “预览态：此处主要用于整理检索意图并跳转配置页”

C. OpenSourcePage

原因： - 当前是意图收集与策略建议，不是实时仓库检索结果页。

建议文案： - “当前为开源比选助手预览” - “输入内容将先整理为比选目标，不直接返回实时候选仓库”

D. SettingsLayout 中的“配置助手”

原因： - 当前主要返回检查清单，不会真实改配置。

建议文案： - “仅生成配置检查建议，不会直接写入设置”

E. ShellContextPanel 的“上下文助手”

原因： - 更偏 UI 辅助入口，不应被理解为当前页的真实智能代理。

建议文案： - “当前为上下文辅助助手，优先提供建议与跳转，不直接执行后台任务”

可选补标识的页面

F. Run Console 中的“运行分析助手”

如果它当前只是基于 RunDetail 本地总结而非真实调用后台分析，可补一句：

  • “基于当前运行详情的本地分析视图”

G. Workflow / Creative 的对话助手

如果它们现在只是把输入写入页面局部状态，而不是正式进入后端编排，可补一句：

  • “当前优先生成页面内步骤草案，执行仍以按钮操作为准”

4. 收口建议

最小收口标准

满足以下条件，即可认为这一批前端改动达到“可收口、可继续提交”的状态：

  • 登录 / 匿名进入逻辑清晰
  • 路由兼容跳转正常
  • Chat → Run Detail 主链可走通
  • Workflow / Creative 至少能进入并完成主操作
  • 关键页面有明确 fallback
  • 演示态页面有清晰标识，不误导用户
  • typecheck 与 build 持续通过

当前建议的下一步

  1. 先按本文第 1 节做页面点击验收。
  2. 验收后把问题分成：阻断 / 非阻断 / 后续优化。
  3. 再按第 2 节拆分提交。
  4. 最后给第 3 节列出的页面补“预览 / 演示态”标识。
