# X-Agent 商用完整交付 Goal 结构设计

- 日期：2026-07-19
- 主题：为 `xagent` 建立一个可长期推进、直到“完整交付”为止的项目级 Goal 长任务结构
- 当前主方案：**项目级母 Goal + 三阶段 Goal + 执行包**
- 适用范围：`xagent` 商用成熟度推进（内部试点 → 正式商用 GA → 企业级长期运营）

---

## 1. 背景与问题定义

当前 `xagent` 已经不是原型，也不再适合用“临时任务列表 + 一次性收口”来管理长期交付。现有项目状态表明：

- 项目具备内部试点 / 受控私有部署基础；
- Spine Phase 1 已经证明系统可以把 goal / taskboard / run / release 作为正式交付主链来组织；
- 但项目距离“商用程度百分百”仍然有明确差距，这些差距横跨三个层次：
  1. 内部试点可稳定使用；
  2. 正式商用 GA；
  3. 企业级长期运营。

如果继续沿用“一个大任务板、所有事情混着推进”的方式，项目会出现三个问题：

1. **阶段混叠**：Phase 2 / Phase 3 的要求会提前压到当前执行里；
2. **优先级漂移**：执行层会不断跳到高阶能力，导致当前阶段收不了口；
3. **汇报失真**：owner 看到的是零碎任务，而不是项目现在处于哪一个商用阶段。

因此，需要为这个项目建立一个**项目级长任务 Goal 结构**，让后续推进围绕阶段门而不是围绕零散任务展开。

---

## 2. 设计目标

本次设计目标是：

> 为 `xagent` 定义一套可以持续推进到“完整交付”为止的 Goal 长任务结构，使项目级目标、阶段目标、执行包和具体任务之间有稳定关系，并保证只激活当前阶段，不让后续阶段提前失控展开。

### 2.1 总目标定义

项目总 Goal 固定为：

- **G0：xagent 商用完整交付**

该 Goal 的终点定义为：

> **Phase 1、Phase 2、Phase 3 全部完成后，才允许关闭。**

也就是说：
- Phase 2 完成不关闭 G0；
- 只有企业级长期运营能力也通过后，G0 才能结束。

### 2.2 设计原则

1. **母 Goal 永不被阶段性完成误关闭**；
2. **三阶段必须串行，不并行激活**；
3. **执行层永远只围绕当前阶段展开**；
4. **每一层都要能清楚汇报状态与阻塞**；
5. **Goal 结构优先于零散任务，先建治理骨架再细化执行。**

---

## 3. Goal 层级结构

### 3.1 母 Goal

- **G0：xagent 商用完整交付**

职责：
- 承载整个项目从准商用到完整交付的唯一总目标；
- 不管理单个测试或修复；
- 只关心当前项目处于哪个阶段、哪个阶段被阻塞、距离完整交付还差哪一层。

### 3.2 阶段 Goal

G0 下面固定挂 3 个阶段 Goal：

- **G1：内部试点可稳定使用**
- **G2：正式商用 GA**
- **G3：企业级长期运营**

职责：
- 每个 Goal 只负责一个商用成熟度阶段；
- 负责维护自己的验收门；
- 负责决定当前阶段是否通过、是否阻塞、是否允许进入下阶段。

### 3.3 执行包层

每个阶段 Goal 下固定拆成 4 个执行包：

#### G1（内部试点）
- **G1-A1：功能链路包**
- **G1-A2：稳定性 / 恢复包**
- **G1-A3：数据 / 权限 / 审计包**
- **G1-A4：试点交付材料包**

#### G2（正式 GA）
- **G2-B1：候选冻结包**
- **G2-B2：目标环境演练包**
- **G2-B3：发布 / 回滚包**
- **G2-B4：签字 / 证据包**

#### G3（长期运营）
- **G3-C1：HA / K8s 包**
- **G3-C2：可观测 / 告警包**
- **G3-C3：审计 / 保留策略包**
- **G3-C4：容量 / 扩展边界包**

职责：
- 执行包是当前阶段的最小治理单位；
- 每个包下面再挂具体执行任务；
- 阶段 Goal 不直接管理 30 个零散任务，而是通过执行包管理推进节奏。

---

## 4. Goal 生命周期规则

### 4.1 母 Goal 关闭条件

G0 只有在下列条件同时成立时关闭：

- G1 = `done`
- G2 = `done`
- G3 = `done`

否则：
- G0 始终保持 `active`
- 如果某一阶段 Goal blocked，则 G0 标记为“受该阶段阻塞”

### 4.2 阶段 Goal 开启条件

#### G1
- 默认立即开启
- 因为当前项目首先要完成内部试点稳定使用

#### G2
只有在 G1 的全部 Gate 通过后才允许开启：
- 功能门通过
- 稳定性门通过
- 权限 / 可追溯门通过
- 试点交付门通过

#### G3
只有在 G2 的全部 Gate 通过后才允许开启：
- 候选冻结门通过
- 发布演练门通过
- 交付治理门通过
- 签发门通过

### 4.3 执行包激活规则

每个阶段下面建议最多维持：

- **1 个 active 执行包**
- **1~2 个 ready 执行包**
- 其余保持 `pending`

这样做的目的是：
- 避免“所有包同时开工”导致管理失焦；
- 保证当前阶段始终有唯一主推进点；
- 降低任务板膨胀速度。

---

## 5. Blocked 规则

### 5.1 哪些层允许 blocked

- 执行包可以 `blocked`
- 阶段 Goal 可以 `blocked`
- 母 Goal 不直接 `blocked`，但可以标记为“受某阶段阻塞”

### 5.2 blocked 必填字段

任何 blocked 项都必须包含：

1. 阻塞原因
2. 需要谁决策
3. 恢复条件
4. 下次检查点

### 5.3 blocked 的目的

blocked 不是一句“卡住了”，而是：

> **让 owner 或主调度看到：卡在哪里、谁能解、解完后继续做什么。**

## 6. 三层任务板视图

### 6.1 视图 A：母 Goal 视图

适用对象：owner / 决策者

只展示：
- G0 当前状态
- 当前激活阶段（G1/G2/G3）
- 当前阶段完成度
- 当前最大阻塞

这个视图不应该展示几十个子任务。
它的职责是回答：

> **项目现在处于哪个商用成熟度阶段？距离完整交付还差哪一层？**

### 6.2 视图 B：阶段 Goal 视图

适用对象：主调度 / TL

展示：
- 当前阶段的 4 个执行包
- 每个包的状态
- 当前 active 包
- 当前 blocked 包
- 当前阶段的 Gate 通过情况

这个视图的职责是回答：

> **当前阶段到底在推进哪一包？哪一包卡住了？**

### 6.3 视图 C：执行包视图

适用对象：执行者 / AI 代理 / 开发者

展示：
- ready
- in_progress
- review
- blocked
- done

这里才挂真正的实现任务、测试任务、文档任务、验证任务。

## 7. 命名规范

为了让 Goal / 包 / 任务之间长期可追踪，命名固定如下：

### 7.1 母 Goal
- `G0 xagent 商用完整交付`

### 7.2 阶段 Goal
- `G1 内部试点可稳定使用`
- `G2 正式商用 GA`
- `G3 企业级长期运营`

### 7.3 执行包
- `G1-A1 功能链路包`
- `G1-A2 稳定性 / 恢复包`
- `G1-A3 数据 / 权限 / 审计包`
- `G1-A4 试点交付材料包`
- `G2-B1 候选冻结包`
- `G2-B2 目标环境演练包`
- `G2-B3 发布 / 回滚包`
- `G2-B4 签字 / 证据包`
- `G3-C1 HA / K8s 包`
- `G3-C2 可观测 / 告警包`
- `G3-C3 审计 / 保留策略包`
- `G3-C4 容量 / 扩展边界包`

命名目标：
- 只看 ID 就知道它在哪一层；
- 只看名字就知道它负责什么；
- 后续汇报和任务板同步能长期一致。

---

## 8. 执行节奏与汇报规则

### 8.1 汇报节奏

#### 母 Goal
- 只在阶段切换或重大阻塞时更新

#### 阶段 Goal
- 每完成一个执行包更新一次

#### 执行包
- 按具体任务推进：测试、修复、文档、验证、提交

### 8.2 每轮必须输出的四件事

每轮推进都应固定输出：

1. 当前激活阶段
2. 当前 active 执行包
3. 当前 blocked 项
4. 下一步唯一优先动作

这样项目汇报不再是“还差很多”，而是：

> 现在处于 G1，当前 active 是 G1-A2，卡在 X，下一步先做 Y。

---

## 9. 当前推荐启动方式

当前不建议一开始就把三阶段全部细化成大量任务。推荐做法是：

### 第一步：建立 Goal 结构
正式建立：
- G0
- G1
- G2
- G3

### 第二步：只激活当前阶段
- G1 = `active`
- G2 = `pending`
- G3 = `pending`

### 第三步：只展开 G1
- G1-A1 = `ready`
- G1-A2 = `ready`
- G1-A3 = `pending`
- G1-A4 = `pending`

### 第四步：先推进 A1 / A2
执行顺序建议：
1. G1-A1 功能链路包
2. G1-A2 稳定性 / 恢复包
3. G1-A3 数据 / 权限 / 审计包
4. G1-A4 试点交付材料包

原因：
- 没有主链稳定，后面的治理没有意义；
- 没有恢复能力，试点容易变成一次性演示；
- 权限 / 审计应建立在主链和状态可见之上；
- 材料包应该基于前 3 项的实际收口结果写，而不是先空写。

---

## 10. 当前结论

这套 Goal 长任务结构的核心价值在于：

- 让 `xagent` 的“商用完整交付”不再依赖零散任务堆积，而是依赖三阶段串行推进；
- 让 owner 看到的是“项目现在处于哪个商用阶段”，而不是几十个细碎任务；
- 让执行层始终只围绕当前阶段工作，防止后续阶段能力提前失控膨胀。

最终结论：

> **推荐采用“项目级母 Goal + 三阶段 Goal + 执行包”的结构来长期推进 `xagent` 的完整交付，并且当前只激活 G1（内部试点可稳定使用），再按 A1/A2/A3/A4 顺序推进。**
