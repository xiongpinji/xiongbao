# TASK PACKAGE PROTOCOL

## 1. 协议目标

让 Claude Code 与 Codex 在同一仓库下共享：

- 同一领取入口
- 同一任务卡格式
- 同一交付语义
- 同一验收标准

从而避免抢任务、重复修、隐式扩 scope、无证据交付。

---

## 2. 任务包最小字段

每个任务包至少要能明确：

1. ID
2. 标题
3. 目标
4. 修改边界
5. 禁止改动
6. 依赖
7. 验收标准
8. 建议验证命令
9. 证据要求

---

## 3. 领取协议

1. 只能领取 `READY` 状态任务
2. 领取前先读取：
   - `docs/coordination/README.md`
   - `docs/coordination/TASK_BOARD.md`
   - `docs/coordination/TASK_PACKAGE_PROTOCOL.md`
3. 领取时先把任务状态从 `READY` 改成 `CLAIMED`
4. 必须一次性补齐：
   - `Owner`
   - `开始时间`
   - `分支/工作树`
   - `依赖`
5. 未补齐这些字段，视为未成功领取，其他代理可继续领取

---

## 4. 实施协议

1. 只能在任务包边界内修改
2. 禁止顺手修不在本包内的问题
3. 若必须跨包改动：
   - 先回任务板写明原因
   - 标注受影响任务包
   - 必要时拆新包
4. 不允许在未声明的情况下扩大 scope

---

## 5. 交付协议

完成后，任务必须先进入 `REVIEW`，并补齐以下 4 项：

1. **改了什么**
2. **怎么验证**（命令 + 输出结果）
3. **剩余风险**
4. **建议 reviewer 重点看什么**

未附证据不得转 `REVIEW`。

---

## 6. 验收协议

Reviewer 只做两件事：

1. 核对任务边界是否被遵守
2. 核对证据是否覆盖验收标准

验收结果只允许：

- 通过：改 `DONE`
- 不通过：退回 `IN_PROGRESS`
- 被阻塞：改 `BLOCKED`

验收阶段不要继续模糊扩 scope。

---

## 7. 阻塞协议

满足以下任一情况，必须写入 `Blocked`：

- 外部依赖不可用
- 环境问题导致无法继续
- 需求或口径冲突
- 持续 30 分钟以上无进展

阻塞记录必须包含：

1. 阻塞原因
2. 需要谁决策
3. 恢复条件
4. 下次检查点

没有恢复条件的阻塞记录视为无效。

---

## 8. 冲突处理

如果 Claude Code 与 Codex 同时盯上同一区域：

- 以**先 CLAIMED 且记录完整**者为准
- 另一方必须撤回或改领其他包
- 不允许“各自先改，最后再合并”

---

## 9. 文档更新协议

如果任务影响以下内容，必须同步更新对应文档，否则任务不能算 `DONE`：

- 真实状态口径
- 发布门禁
- 默认值基线
- 协作规则

典型涉及：

- `docs/COMMERCIAL_STATUS_SOURCE_OF_TRUTH.md`
- `docs/COMMERCIAL_RELEASE_CHECKLIST_V1.md`
- `docs/coordination/*`

---

## 10. 推荐首批任务包

- `P0-A orchestration await bug`
- `P0-B 前端 lint`
- `P0-C preview/demo 污染清理`
- `P0-D 危险默认值`
- `P0-E CI 最小门禁与真实状态文档对齐`

---

## 11. 执行会话持续运行协议

如果目标是“用户不做人肉中转”，执行会话必须遵守以下额外规则：

1. 完成一个任务并写完 `delivery-report.md` 后，不要直接退出会话。
2. 若任务板中仍有 `READY` 任务，继续自动领取下一包。
3. 若任务板中暂时没有 `READY` 任务：
   - 保持会话驻留
   - 按固定周期重新读取 `docs/coordination/TASK_BOARD.md`
   - 直到出现新任务、进入阻塞、或阶段被明确结束
4. 执行会话若准备停止，必须先在任务板中明确：
   - 当前任务是否已交付
   - 是否进入 `BLOCKED`
   - 是否需要总调度接管

### 执行会话对总调度的最小暴露要求

执行会话必须把以下内容落到仓库中，供总调度读取：

1. 任务当前状态（在 `TASK_BOARD.md` 中）
2. 已完成的验证命令与结果（在 `delivery-report.md` 中）
3. 剩余风险
4. reviewer 关注点
5. 若阻塞，必须写出恢复条件
6. 若发现边界漂移，必须写出跨包声明或新拆任务建议

### 执行会话必须显式落盘给总调度看的输出

以下内容不得只停留在聊天窗口，必须同步写入任务板、`delivery-report.md` 或任务专属报告：

1. **当前状态变化**：例如 `CLAIMED -> IN_PROGRESS -> REVIEW -> DONE / BLOCKED`
2. **关键问题**：当前真正卡在哪里，而不是笼统写“有问题”
3. **剩余风险**：哪些没有收口、哪些只是本地证据、哪些不能替代正式发布证据
4. **恢复条件**：需要的 secret、账号、依赖服务、命令、外部决策
5. **Reviewer 关注点**：下一位审查者最应该核什么
6. **下一步动作建议**：如果当前包完成/阻塞，建议后续总调度拆什么或恢复什么

### 总调度的读取优先级

总调度应优先读取：
1. `docs/coordination/TASK_BOARD.md`
2. `docs/coordination/reports/delivery-report.md`
3. 任务专属报告（如 `R10_FULL_FLOW_E2E_TRIAGE.md`、`R16_FULL_MODE_REHEARSAL_PREP.md`、`R17_PR_EVIDENCE_MATRIX_SOURCE.md`）

如果一个重要状态只存在于聊天窗口而未落盘，总调度应视为“状态暴露不足”，并要求执行会话补齐。---

## 12. 无任务时的默认策略

当执行会话发现：
- 当前没有 `READY` 任务
- 自己也没有未完成的 `IN_PROGRESS` / `REVIEW` 任务

默认动作不是退出，而是：

1. 记录“当前空闲，等待下一任务”
2. 定期重读任务板
3. 若总调度新建任务包，则自动进入下一轮领取

只有在以下情况之一成立时，才允许真正停止：
- 用户明确要求停止
- 阶段结束且总调度已宣布封板
- 外部环境强制中断，且已把状态回写到任务板

---

## 13. 自动拆解补单协议

若目标是“让 Claude Code 与 Codex 始终有任务可做，直到所有修复完毕”，总调度必须执行持续补单，而不是等用户再次分派。

### 水位规则

主调度必须维持：
- **至少 2 张 Codex 可领取的 `READY` 卡**
- **至少 1 张 Claude Code 当前卡 / 解阻卡**

一旦低于该水位，就必须立即补单。

### 触发条件

以下任一发生时，立即重新扫描并补单：
1. 有任务进入 `DONE`
2. 有任务进入 `BLOCKED`
3. `READY` 中 Codex 可领取任务少于 2 张
4. Claude Code 没有当前卡或解阻卡
5. `delivery-report.md` 新增一节，且该节暴露新的 `剩余风险` / `Reviewer 关注点` / `未形成` / `仍需` / `尚未` 等闭环缺口
6. 当前仍在执行 / 待审的任务已经足以暴露下一批缺口（例如 full-flow 未跑、audit 风险未处置、R9 证据已完成但状态未同步），即使这些任务还没完全 DONE 也要提前补下一包

### 任务来源优先级

总调度补单时，按以下顺序抽取下一批任务：

1. `docs/coordination/reports/delivery-report.md`
2. `docs/COMMERCIAL_RELEASE_CHECKLIST_V1.md`
3. `docs/COMMERCIAL_STATUS_SOURCE_OF_TRUTH.md`
4. `docs/superpowers/plans/2026-07-05-commercial-readiness-execution-plan.md`
5. 已完成或待审任务的 `剩余风险` / `Reviewer 关注点`（例如未覆盖的 full-flow E2E、npm audit 风险、bundle 告警、SQLite/Alembic 漂移、页面截图验收缺口）
6. 任务板与交付记录之间的状态 / 证据漂移（例如任务板遗漏 R9/R13/R14 的状态同步）
7. `docs/coordination/README.md` 与 `docs/coordination/TASK_PACKAGE_PROTOCOL.md`（仅在需要修协议时使用）

### 命名规则

- 当前阶段统一使用前缀：`R` = PR 审查准备 / 发布证据补齐
- 为 `BLOCKED` 任务服务的解阻包统一使用前缀：`U`
- 若任务需要拆成多个子包，使用 `Rn-A`、`Rn-B` 命名
- 不要把新补单命名回 `P0-*`，避免阶段混淆

### Owner 分配规则

- Claude Code 固定承担：总调度、解阻包、远端 CI / PR / gate 包、最终 PR 组装包
- Codex 固定优先承担：build 证据、E2E 冒烟、截图验收、runbook、环境基线、文档补齐等边界清晰包
- 任何任务只允许一个主 Owner；协同方只写在依赖或 reviewer 关注点里

### 去重规则

补单前必须检查任务板 `READY / IN_PROGRESS / BLOCKED / REVIEW / DONE` 五区，若已有同验收摘要任务，则不得重复建卡。

### 封板条件

只有当以下条件同时满足时，主调度才允许停止补单：
- `TASK_BOARD` 中无 `READY`
- 无可恢复 `BLOCKED`
- `delivery-report` 中无未闭环剩余风险
- 当前阶段发布检查表条目全部有证据映射

---

## 14. 收尾阶段的等待不是自动故障

当系统进入 PR 审查准备 / 发布证据补齐阶段后，执行会话可能出现“当前没法立刻继续”的状态。这时应按下面规则判断：

### 这是正常依赖门控等待，当且仅当：
1. 任务板里已经明确写出当前 `BLOCKED` / `IN_PROGRESS` / `REVIEW` 的状态
2. 阻塞原因与恢复条件已写清
3. 总调度已提前补齐 READY 水位或明确没有可拆的新包
4. 当前不启动某任务（例如 R5）是因为依赖未满足，而不是因为忘了推进

### 这才算协调故障：
1. 当前没有 `READY`，但总调度也没有补后续包
2. 执行会话停住后，任务板没有任何阻塞原因或恢复条件
3. REVIEW 区与交付报告长期漂移，无人回写状态
4. gate 依赖已满足，但任务仍无故不推进

### 收尾阶段默认推进顺序
1. 先补解阻包（U*）或环境前置包（如 R16）
2. 再补证据一致性 / 证据矩阵包（如 R15 / R17）
3. 最后再启动最终 PR 包（R5）

### 红线
- 不因为“暂时没有可抢的包”就误判为系统停摆
- 不在 R4 / R8 未收口前强推 R5
- 不为了让执行会话看起来忙而创造无价值新卡
