# G3-C4 容量 / 扩展边界包

> 适用阶段：G3 企业级长期运营
>
> 用途：冻结 `xagent` 在企业级长期运营阶段的容量边界、扩缩容方向、性能口径和试点用户规模限制，避免系统进入长期运营后再靠经验猜测“能撑多少、哪儿会先坏”。

---

## 1. 目标

G3-C4 的目标是：

> **把企业级长期运营阶段的容量、扩展边界和瓶颈认知冻结成一个可执行包。**

这一步不要求立即完成大规模压测平台，也不要求把所有扩容策略一次性工程化完毕；它只负责：

- 明确当前已知容量边界；
- 明确高风险瓶颈点；
- 明确扩缩容时应先验证什么；
- 明确试点 / 灰度 / 企业级规模之间的差别。

---

## 2. 当前已有基础

当前已经具备的基础包括：

- G2 阶段已完成正式商用 GA 的候选冻结、演练、发布 / 回滚与签字包；
- `docs/COMMERCIAL_RELEASE_CHECKLIST_V1.md` 中已存在性能与容量检查条目；
- `docs/OPERATIONS_MANUAL_V1.md` 中已有 worker、依赖、排障、恢复的最小值守路径；
- `docs/ENVIRONMENT_BASELINE_V1.md` 中已明确环境分层与依赖边界；
- 代码层已有 API / worker / web 主链与任务 / workflow / run 读模型。

---

## 3. 当前缺口

### 3.1 容量边界缺口

当前仍未冻结：
- 试点 / 灰度 / 企业级之间的用户规模分界；
- API / worker / 依赖的最低合理容量；
- 哪些负载模式属于已知可接受，哪些属于超载风险。

### 3.2 性能口径缺口

当前仍未冻结：
- P95、错误率、队列积压、冷启动 / warmup 的长期运营门槛；
- 哪些性能劣化属于告警级别；
- 哪些性能问题必须先阻止扩容。

### 3.3 扩展策略缺口

当前仍未冻结：
- API / worker 的横向扩展最低前提；
- 多实例下的状态一致性前提；
- 资源 / 配额 / 限流策略的长期运营规则。

---

## 4. 必须冻结的容量对象

G3-C4 至少要把以下对象列为容量评估对象：

- API 请求吞吐
- worker 任务处理吞吐
- 登录 / 提交 / 查看运行详情链路
- 后台队列积压
- LLM provider 响应时间与失败率
- Redis / Postgres / Qdrant 依赖能力

这些对象的关键要求是：
- 能定位瓶颈；
- 能知道先扩谁；
- 能判断何时不能再继续扩大范围；
- 能支持企业级长期运行的最小容量说明。

---

## 5. 试点 / 灰度 / 企业级规模边界

当前至少应冻结如下边界口径：

### 5.1 试点规模
- 适合少量内部使用者；
- 可以接受人工介入排障；
- 不以极限吞吐为目标。

### 5.2 灰度规模
- 能稳定服务受控外部用户；
- 能观察性能退化和队列积压；
- 能在扩容前识别瓶颈。

### 5.3 企业级规模
- 需要明确容量基线；
- 需要明确扩缩容方式；
- 需要明确主要依赖的瓶颈与保护策略。

---

## 6. 最小验证口径

### 6.1 基础负载检查

至少应有以下检查入口：

```bash
cd apps/api
pytest -q
```

以及必要时的负载检查：

```bash
cd apps/api
locust -f tests/load/locustfile.py --host http://localhost:8000 --headless -u 50 -r 5 -t 60s
```

### 6.2 容量结论记录

容量结论至少记录：
- 当前试点用户规模
- 当前可接受并发量
- worker / queue backlog 的预警阈值
- LLM 调用瓶颈
- 依赖服务中的主要瓶颈点

---

## 7. 最小通过标准

G3-C4 要通过，至少需要满足：

1. 企业级长期运行的容量边界已明确；
2. 关键瓶颈对象已列出；
3. 扩缩容前提已描述；
4. 试点 / 灰度 / 企业级规模的分界已写清；
5. 团队不会再把“还没测过容量”误写成“已经可无限扩展”。

这意味着：
- G3-C4 的“通过”不是性能测试全覆盖；
- 而是容量边界、瓶颈与扩展方向已经被正式定义。

---

## 8. 当前结论

G3-C4 的作用不是建立一套完整性能平台，而是：

> **把企业级长期运营阶段的容量上限、扩展边界和主要瓶颈冻结成一份可执行包。**

完成 G3-C4 后，G3 的四个核心方向就具备了完整的治理骨架。
