# Roadmap v2 C 容量与性能增强真实验证计划

> 适用阶段：Roadmap v2
>
> 用途：把 C 容量与性能增强包从“方向定义”推进到“可执行验证”，明确当前压测入口、瓶颈对象、容量结论与扩容建议的验证范围、方法与证据要求。

---

## 1. 目标

本计划的目标是：

> **为 `xagent` 的容量与性能增强路线提供第一份真实验证计划，使 C 包不再停留在方向层，而进入可验证状态。**

---

## 2. 验证范围

本次验证只覆盖以下内容：

1. 当前是否已有真实可执行的压测入口；
2. 当前是否已经有正式列出的容量检查项；
3. 当前瓶颈对象是否已被明确识别；
4. 当前试点 / 灰度 / 企业级规模边界是否已可解释；
5. 当前哪些结论是“已验证”，哪些仍只是后续目标。

本次验证**不**要求一次性完成：
- 完整性能平台建设；
- 所有容量结论的生产级签字；
- 多地域 / 大规模容量实测；
- 所有扩缩容策略自动化落地。

---

## 3. 验证环境

当前优先采用：
- 仓库中已有性能 / 容量材料与真实命令入口的等价验证环境；
- 用于确认压测入口、容量检查项、瓶颈对象和规模边界是否具备真实材料基础。

环境前提：
- 能读取 `COMMERCIAL_RELEASE_CHECKLIST_V1.md` 的性能与容量条目；
- 能读取 `OPERATIONS_MANUAL_V1.md` 中的 backlog / warmup / 依赖风险入口；
- 能确认 `tests/load/locustfile.py` 是否存在并可被引用。

---

## 4. 验证项

### 4.1 压测入口验证

检查：

```bash
cd apps/api
locust -f tests/load/locustfile.py --host http://localhost:8000 --headless -u 50 -r 5 -t 60s
```

期望：
- 至少有一条被正式文档引用的负载测试入口；
- 不是口头设想，而是可执行入口。

### 4.2 正式容量检查项验证

验证：
- `COMMERCIAL_RELEASE_CHECKLIST_V1.md` 中是否已列出：
  - 至少一轮负载测试
  - 基础容量结论（如 10/50/100 并发建议）
  - 关键瓶颈点
  - 试点用户规模与限制条件

期望：
- 容量与性能不再是完全空白；
- 已有正式检查项。

### 4.3 关键瓶颈对象验证

验证当前是否已明确列出：
- API 请求吞吐
- worker 任务吞吐
- LLM provider 响应时间与失败率
- Redis / Postgres / Qdrant 能力
- worker backlog / warmup / timeout 风险

期望：
- 团队知道先看哪几个瓶颈；
- 不再把容量问题当成黑盒。

### 4.4 规模边界验证

确认当前是否已明确区分：
- 试点规模
- 灰度规模
- 企业级规模

期望：
- 不把“可试点”误说成“可无限扩展”；
- 规模边界已形成书面表达。

---

## 5. 通过标准

C 容量与性能增强包的真实验证通过，至少需要满足：

1. 压测入口已真实存在并被正式引用；
2. 容量检查项已被正式列出；
3. 关键瓶颈对象已被明确；
4. 规模边界已有书面表达；
5. 可以明确区分“当前已有基础”与“后续仍需更深实测的部分”。

这意味着：
- C 包的“通过”不是所有容量结论都已经被完整实测；
- 而是容量增强已经进入真实可执行验证阶段。

---

## 6. 证据要求

本计划要求输出的最小证据包括：

- 当前压测入口说明
- 容量检查项确认结果
- 当前关键瓶颈对象清单
- 试点 / 灰度 / 企业级规模边界确认结果
- 最终判定：
  - 通过 / 不通过
  - 哪些已验证
  - 哪些仍是后续目标

建议归档到：
- `docs/coordination/reports/roadmap-v2-capacity-verification.md`

---

## 7. 当前结论

当前 `C 容量与性能增强包` 已完成方向定义；
这份计划的作用是让它进入下一状态：

> **可执行验证**

只有完成这一步，`C 容量与性能增强包` 才能从“方向定义”走向“验证完成”。
